# Project-scoped persistent agent Atomspaces

## User contract

A project is the top-level ownership and isolation boundary. Every role, task,
agent identity, session attempt, Atomspace, note, schedule, board projection,
Oh My Goals database, and audit record belongs to one project.

Each project agent has:

- a generated stable identifier;
- one current role selected through the MeTTa policy;
- a private runtime Atomspace;
- a durable canonical `.metta` file;
- zero or more Agent Orchestrator session attempts;
- notes that survive session termination and daemon restart.

The project also has a shared Atomspace. Private notes do not become shared
project facts unless a later explicit publication operation is introduced.

## Versioned specification contract

The new surface is opt-in through `thread-spec-v2` and
`goalchainer-thread-v2`. Existing `thread-spec-v1` inputs, protocol records,
plans, and audit files keep their current meaning. A v1 role value must not be
silently reinterpreted as a durable Agent Orchestrator identity.

A v2 MeTTa Markdown specification declares:

```metta
(thread-spec-v2 incident-42)
(thread-project incident-42 "ao-project-id")
(thread-agent incident-42 evidence-worker)
(thread-role incident-42 worker evidence-worker)
(thread-atomspace-link incident-42 project-shared shared project)
(thread-atomspace-link incident-42 worker-private private evidence-worker)
```

An agent key such as `evidence-worker` is a stable semantic symbol. Agent
Orchestrator resolves the pair of project ID and agent key to a generated UUID.
The source never contains that UUID or a filesystem path.

MeTTa validates the agent registry, role ownership, task routing, and logical
Atomspace visibility. The dispatch result contains the project, selected role,
agent key, attempt key, MCP profile, workflow, and logical Atomspace links.
Python transports that record unchanged. Agent Orchestrator creates or finds
the stable agent, starts a session attempt, and returns the generated agent and
session IDs. MeTTa then validates those returned bindings before they enter the
audit or UI projection.

The v2 UI protocol separates these identities:

- `agentKey` is the semantic key selected by MeTTa;
- `agentId` is the durable UUID generated by Agent Orchestrator;
- `sessionId` identifies one execution attempt;
- `assignedRole` is the role selected by MeTTa;
- `sessionAttempts` records the full attempt history.

## Authority boundary

| Concern | Authority |
|---|---|
| Project, role, task, and agent declarations | Mettabase MeTTa Markdown |
| Role eligibility and task-to-agent assignment | GoalChainer MeTTaScript |
| Durable task lifecycle | OmegaClaw `lib_directive` |
| Stable project-agent records and session-attempt links | Agent Orchestrator SQLite |
| Canonical agent note facts | Per-agent `.metta` file under `AO_DATA_DIR` |
| Worktrees, processes, terminals, and transcripts | Agent Orchestrator |
| UI display | Read-only projection of the authorities above |

Python and Go perform parsing, validation, persistence, file locking, atomic
replacement, process execution, and API transport. They do not infer role
eligibility or select an agent when the same conclusion can be expressed as a
MeTTa graph rewrite.

## Storage rules

Runtime state must not dirty a source repository. Agent Orchestrator stores it
under:

```text
AO_DATA_DIR/mcp/oh-my-goals/projects/<project-key>/atomspaces/
  shared.metta
  agents/<agent-id>/notes.metta
```

The project key is a SHA-256 digest of the validated Agent Orchestrator project
ID. The filename owner resolves the generated agent ID inside that project.
The API never accepts a filesystem path. Atomspace files use canonical MeTTa
facts, bounded strings and collections, file locking, mode `0600`, and atomic
replacement. A failed write must leave the prior valid file readable.

Oh My Goals writes the snapshot from the live MeTTa proposition facts by using
MeTTaScript's canonical formatter. Its SQLite event store remains the restart
log. The host owns directory confinement, a persistent sidecar lock, a
same-directory temporary file, file and directory `fsync`, and atomic rename.
MeTTa owns which propositions are active and visible.

Agent Orchestrator passes only paths it derived under its data directory:

```text
OH_MY_GOALS_PROJECT_ATOMSPACE_PATH=<project-root>/shared.metta
OH_MY_GOALS_ATOMSPACE_PATH=<project-root>/agents/<agent-id>/notes.metta
OH_MY_GOALS_AGENT_ID=<generated-agent-id>
OH_MY_GOALS_SESSION=<agent-orchestrator-session-id>
OH_MY_GOALS_ATTEMPT=<stable-agent-attempt-number>
```

The shared file contains project and derived scopes. The private file contains
only the stable agent's session scope. Oh My Goals uses
`OH_MY_GOALS_AGENT_ID` as that scope's durable namespace while retaining
`OH_MY_GOALS_SESSION` as the current execution-attempt identity in its runtime
metadata. User-scope memory is not copied into either project-owned file. A
writer takes the file lock and reads a fresh SQLite view before rendering, so
concurrent project agents cannot replace the shared snapshot with a stale
subset.

Each snapshot starts with one inert identity fact:

```metta
(MemorySnapshot oh-my-goals-atomspace-v1 agent "ao-project-id" "agent-uuid")
```

The shared variant uses `project` and an empty agent string. Remaining lines are
canonical, sorted `MemoryProposition`, `MemoryContent`, `MemoryState`,
`MemoryRecordedAt`, `MemoryTree`, `MemorySource`, `MemoryAssertionState`,
`MemorySourceTruth`, `MemoryDerivation`, `MemorySupersedes`, and `ClaimCore`
facts. The API parses only this closed data schema. It never evaluates the file.

## Identity rules

An Agent Orchestrator session is one execution attempt, not the durable agent
identity. A project agent can own several sequential attempts. Agent IDs are
globally unguessable and every database lookup also checks the project ID.
Terminating a session does not delete the agent record or its `.metta` file.

The initial implementation supports one current role and immutable role
assignment history. Reusing an agent in another project is forbidden. A later
knowledge-export operation can copy selected facts explicitly without sharing
private files or databases.

Agent Orchestrator allocates attempt numbers independently of GoalChainer task
attempt numbers. The relation between a project agent, attempt number, and
session is immutable. Replaying the same GoalChainer source-task key with the
same agent returns the existing attempt. Replaying it with another agent fails
as a typed conflict.

The Agent Orchestrator API exposes bounded agent metadata, attempt links, and a
read-only note projection. Note mutations go through the typed Oh My Goals MCP
tools so an HTTP caller cannot inject executable MeTTa or choose a path.

## Integrated Agent Orchestrator revisions

Agent Orchestrator commit
`4d1e8a659b199ef586fa6462f83ff0d4f98cb60c` implements the project-agent
records, persistence, read-only note projection, UI, and Oh My Goals MCP
integration. Commit `e459dafbab53085575840067f466d1b03196dd0a` adds the
SQLite-authoritative v2 projection check. A projection PUT must match bound
agent UUID, semantic key, role, attempt number, and session ID before Agent
Orchestrator accepts it.

## Required demonstration

The checked demo must prove:

1. two projects receive separate storage roots;
2. a MeTTa role rule assigns a stable agent to a released task;
3. the first session adds a note;
4. a later session for the same agent reloads that note;
5. a different agent cannot read it;
6. terminating either session leaves the `.metta` file intact;
7. the UI/API expose the agent, role, attempts, and bounded note projection.
